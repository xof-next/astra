# Astra Script 1.0.1

Astra is a C++17 language runtime with a JavaScript-inspired syntax, a native command-line interface, and a built-in standard library. This repository contains the compiler and interpreter source for Astra 1.0.1.

Version 1.0.1 focuses on bounded HTTP server concurrency, request and response resource limits, safer request deadlines, portable native threading, and clearer platform build instructions. It remains an interpreted language preview: it does not compile Astra source into native machine code and it is not a security sandbox.

## Highlights

- C++17 runtime and native `astra` CLI.
- JavaScript-inspired declarations, functions, arrow functions, closures, `async fn`, and `await` syntax backed by a bounded native worker executor.
- 37 built-in standard modules and 172 registered exports, including networking, HTTP clients, HTTP server routing, DNS, TCP, TLS clients, JSON, filesystem access, cryptography, compression, text processing, and collections.
- Version-aware CLI installation through the repository-root `pack.json` manifest.
- HTTP server with a fixed worker pool, bounded pending queue, explicit overload responses, per-IP and total connection limits, request-rate limits, buffer limits, and an absolute request-read deadline.
- Optional native `astra.conf` runtime configuration for server and outbound HTTP client defaults, with strict validation and safe built-in defaults.
- CMake build configuration for POSIX sockets and Windows Winsock.

## Requirements

| Requirement | Minimum / notes |
|---|---|
| CMake | 3.16 or newer |
| C++ compiler | C++17; GCC 9+, Clang 10+, or a supported MSVC toolset |
| libcurl | Development headers and a TLS-enabled build |
| zlib | Development headers and library |
| Threads | A CMake-supported native thread implementation |
| Python | Python 3 for the full integration test suite |
| Git | Required only when cloning the source repository |

Astra links against libcurl and zlib. Install the development packages for the target operating system before configuring CMake.

## Build from source

Clone the repository and enter the 1.0.1 source directory:

```sh
git clone https://github.com/xof-next/astra.git
cd astra/versions/1.0.1
```

On Linux and macOS, use the supplied build script:

```sh
./scripts/build.sh
```

The script configures a Release build, compiles Astra, and executes the CTest suite. To run the steps manually:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure --parallel 2 --timeout 60
```

The generated executable is `build/astra` on Linux, macOS, and Termux. On a multi-configuration Windows generator it is normally `build/Release/astra.exe`.

## Install the CLI

After a successful build, run the installer from this source directory:

Linux, macOS, and Termux:

```sh
./build/astra init
```

Windows PowerShell:

```powershell
.\build\Release\astra.exe init
```

The installer places Astra in the user-level executable directory. Add that directory to the user's `PATH` if the installer does not update it automatically. Open a new terminal and verify the installed executable:

```sh
astra --version
astra --help
```

Astra versions are stored separately. The active runtime can be changed without deleting other installed versions:

```sh
astra versions
astra install 1.0.0
astra use 1.0.0
astra use 1.0.1
```

`astra install` without a version selects the `new` version from the repository-root `pack.json`. Online install and update commands require matching GitHub Release assets and SHA-256 metadata to have been published for the target platform. A source checkout by itself does not provide those release binaries.

## Create and run a project

Create a new application directory:

```sh
mkdir hello-astra
cd hello-astra
astra init --project
```

The generated project includes an `Astra.toml` manifest, an `astra.conf` runtime configuration, and starter source files. The configuration file is introduced in 1.0.1 and is not read or generated by 1.0.0. A minimal manifest is:

```toml
[project]
name = "hello-astra"
version = "1.0.0"
entry = "main.astra"
```

Create `main.astra`:

```astra
pub fn main() {
    console.log("Hello from Astra");
}
```

Run the project or a source file:

```sh
astra
astra run main.astra
astra check main.astra
```

Astra also supports extensionless source paths with `astra run`. Project task aliases can be declared under `[devDependencies]` in `Astra.toml`; task values are restricted to Astra source invocations and are not executed through a shell.

## HTTP server

The `std:server` module creates a native HTTP/1.x server. The API supports route registration, route parameters, request headers and query values, fixed-length request bodies, and JSON or text responses.

### Minimal example

Create `server.astra`:

```astra
import "std:server" as http;

const app = http.create();

app.get("/", (req, res) => {
    res.send("Astra server is running");
});

app.get("/users/:id", (req, res) => {
    res.json({ id: req.params.id, method: req.method });
});

app.post("/echo", (req, res) => {
    res.status(201);
    res.send(req.body);
});

app.listen(3000);
```

Start the server:

```sh
astra run server.astra
```

Test it from another terminal:

```sh
curl -i http://127.0.0.1:3000/
curl -i http://127.0.0.1:3000/users/42
curl -i -X POST http://127.0.0.1:3000/echo --data 'hello'
```

The default bind address is `127.0.0.1`, which accepts local connections only. Set `host` to `0.0.0.0` only when the service is meant to accept connections from external interfaces and the network firewall is configured.

### Runtime configuration

A project created with `astra init --project` receives an `astra.conf` file. The file controls server worker and queue limits, concurrent connections per IP and in total, request-rate limits, server request/response/header buffers, timeouts, and the outbound `std:launch` HTTP client defaults. The file is optional; built-in safe defaults remain active when it is absent.

Validate it before starting the service:

```sh
astra config check
```

The process reads the configuration from its working directory. Use `ASTRA_CONFIG` to select another path. Explicit options passed to `app.listen()` or `launch.*()` override the matching file defaults. See [the runtime configuration reference](docs/CONFIGURATION.md) for every setting, supported range, units, and precedence rules.

`astra.conf` is new in 1.0.1. The 1.0.0 runtime does not load it, so an existing 1.0.0 installation remains unaffected by this feature.

### Routes and request data

Convenience methods are `get`, `post`, `put`, `patch`, `delete`, `head`, `options`, and `all`. The generic method is `route(method, path, handler)`.

The request object exposes:

| Property | Description |
|---|---|
| `req.method` | Uppercase HTTP method |
| `req.url` | Request target, including query string |
| `req.path` | Path without query string |
| `req.params` | Decoded named route parameters |
| `req.query` | Decoded query key/value strings |
| `req.headers` | Request headers with lowercase names |
| `req.body` | Request body as a string |

The response object exposes:

| Method | Description |
|---|---|
| `res.status(code)` | Set an HTTP status from 100 through 599 |
| `res.setHeader(name, value)` | Set a response header; `Server` is reserved |
| `res.send(value)` | Send a stringified response body |
| `res.end([value])` | End the response with an optional body |
| `res.json(value)` | Serialize a value as JSON and set the JSON content type |

Astra supplies `Server: Astra`, `Content-Length`, a default text content type, and `Connection: close`. Applications cannot override the reserved `Server`, `Content-Length`, or `Connection` headers.

### Listener options

All listener options are optional and validated before the socket starts listening.

| Option | Default | Accepted range / format | Description |
|---|---:|---|---|
| `host` | `127.0.0.1` | Non-empty hostname or IP | Local address to bind |
| `workers` | Hardware thread count, capped at 32; minimum default 2 | 1–128 | Fixed number of worker threads |
| `queueCapacity` | `workers * 64` | 1–65536 | Maximum pending accepted sockets, excluding sockets currently handled by workers |
| `backlog` | `256` | 1–65535 | Requested operating-system listen backlog; the OS may clamp it |
| `maxRequests` | `0` | 0–2147483647 | Accepted TCP connections before shutdown; `0` means no configured limit |
| `maxRequestBytes` | `1048576` | 1–67108864 bytes | Maximum request body size |
| `maxResponseBytes` | `4194304` | 1–67108864 bytes | Maximum body accepted by response methods |
| `maxHeaderBytes` | `65536` | 1024–1048576 bytes | Maximum accumulated request-header size |
| `timeoutMs` | `10000` | 100–120000 ms | Absolute deadline for receiving headers and body, plus socket send/receive inactivity timeout |

When the pending queue is full, Astra sends HTTP `503 Service Unavailable` with `Retry-After: 1`, then closes the connection. It does not create an unlimited queue or spawn a thread for every connection. If a handler tries to send a response larger than `maxResponseBytes`, the handler fails and Astra returns HTTP `500 Internal Server Error`.

For complete operational guidance, resource planning, supported HTTP behavior, and deployment recommendations, see [docs/SERVER.md](docs/SERVER.md).

## Concurrency and capacity

Astra accepts connections on one listener thread and dispatches accepted sockets to a fixed-size worker pool. Workers can concurrently receive request data, parse requests, prepare responses, and write to clients. The pending queue has a configured upper bound. When the queue is full, further connections are rejected with HTTP 503.

Astra route callbacks are intentionally serialized per server instance. Route functions may capture mutable interpreter environments, and this interpreter does not provide isolated execution contexts for concurrent evaluation of the same captured environment. The mutex prevents unsafe simultaneous mutation, but it also means that CPU-heavy or blocking route callbacks execute one at a time. Increasing `workers` improves connection I/O concurrency; it does not make Astra handler code execute in parallel.

The current server handles one HTTP request per TCP connection and closes the connection after the response. It supports HTTP/1.0 and HTTP/1.1 request lines with fixed `Content-Length` bodies. It does not implement keep-alive, chunked transfer decoding, HTTP/2, HTTP/3, QUIC, WebSocket upgrades, streaming responses, TLS server sockets, or a JavaScript-compatible event loop.

There is no honest universal request-per-second guarantee. Capacity depends on handler cost, connection churn, payload size, CPU, memory, file descriptors, kernel limits, network bandwidth, and reverse-proxy configuration. The included concurrent integration test is a functional smoke test, not a large-scale capacity benchmark.

## Platform support

Astra uses C++17, CMake, libcurl, zlib, the C++ threading library, and native socket APIs. The source includes a POSIX socket implementation and a Windows Winsock implementation.

| Platform | Build path | Validation in this delivery |
|---|---|---|
| Ubuntu | Native CMake build | Not executed in this environment |
| Debian 13 x86_64 | Native CMake build | Release build and all 39 CTest cases passed |
| Other Linux distributions | Native CMake build with matching development packages | Not all distributions and libc variants tested |
| Windows x64 | MSVC or supported MinGW toolchain, libcurl and zlib | Not executed in this environment |
| Windows ARM64 | Matching ARM64 compiler and dependency packages | Not executed in this environment |
| macOS | Xcode Command Line Tools and Homebrew libraries | Not executed in this environment |
| Android / Termux | Android NDK cross-build for `arm64-v8a` | CI artifact target; device execution still requires validation |

Detailed dependency and command instructions for each platform are in [docs/INSTALLATION.md](docs/INSTALLATION.md). The release workflow builds a separate Android ARM64 executable with the Android NDK for the `arm64-v8a` ABI. It is not the desktop Linux ARM64 binary and should not be assumed to run on desktop Linux. Device execution still requires validation on supported Termux installations; universal Android packages are not provided.

## Tests

Build Astra first, then run:

```sh
ctest --test-dir build --output-on-failure --parallel 2 --timeout 60
```

The current test suite includes language and standard-library tests, CLI and manifest checks, HTTP client and server integration, concurrent HTTP connection handling, runtime configuration validation and enforcement, request deadline and response-size checks, TCP integration, TLS verification, and project initialization.

For a repeatable concurrency measurement, use a dedicated test host and record the exact binary build, CPU, memory, worker count, queue capacity, payload size, client concurrency, test duration, CPU utilization, memory use, and error rate. Do not infer a production capacity figure from the functional smoke tests.

## Current limitations

Astra 1.0.1 is an interpreter preview. It does not provide native code generation, a formal complete language specification, a JavaScript event loop, promise chaining methods, parallel execution of shared handler environments, complete Unicode language semantics, or a production security sandbox. The HTTP server is a bounded HTTP/1.x service component, not a replacement for Nginx, Caddy, HAProxy, Envoy, or a managed edge platform.

For public deployments, place Astra behind a maintained reverse proxy or load balancer. Terminate TLS at that layer, enforce connection and request limits, apply rate limiting, configure access logging, and keep the Astra listener bound to a private interface when practical.
